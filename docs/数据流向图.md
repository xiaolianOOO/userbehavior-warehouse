# 数据流向图（每层存哪、存了什么）

> 这份文件回答四件事：**数据被做了什么处理 / 处理完长什么样 / 存在电脑哪个位置 / 那个文件夹里存了什么**。
> 每次跑完一个脚本、数据发生变化，就回来更新一次。更新方法见文末「维护规则」。

![架构图](architecture.png)

## 0. 三个必须先记住的概念

| 你在数据库里说的 | 在磁盘上长什么样 | 说明 |
|---|---|---|
| 一张表 | 一个**文件夹** | 文件夹名就是表名，例如 `user_behavior` |
| 一个分区 | 一个**带 `=` 的子文件夹** | 例如 `dt=2017-11-25`，查某一天时不用扫全表 |
| 一批数据 | 一堆 `.parquet` 文件 | `part-00000` 到 `part-00027` 是**同一天的数据碎片**，不是28个不同的东西 |

> 一句话：**Spark 写表 = 建文件夹；读表 = 把文件夹里所有 parquet 拼回来。**
> 所以不要去"打开某个 parquet 看一天的数据"，那样看不到完整的一天。

### ⑩ `data\ads\ads_funnel\`｜ADS 集合漏斗

| 项 | 内容 |
|---|---|
| 绝对路径 | `F:\data_warehouse\data\ads\ads_funnel\` |
| 是什么 | 9 行，每天一行；回答"进来的人有多少走到了下单" |
| 存了什么 | `dt`、`uv`、`s1_uv`、`s2_uv`、`s3_uv`、`buy_total_uv`、`buy_pv_nocart`、`buy_nopv_cart`、`buy_nopv_nocart`、`r1`、`r2`、`r_total` |

### ⑭ AI 问数层（程序，不产生数据）

| 项 | 内容 |
|---|---|
| 是什么 | 8 个脚本组成的"服务员"，**不新建任何表**——所有数字都从前面 7 张 parquet 现算 |
| 数据从哪来 | DuckDB 直接读 parquet，挂成 7 个视图（`ai_bootstrap.py`），7 个行数锚点全对 |
| 链条 | `ai_metrics`（19 条指标口径）→ `ai_semantic`（指标计划 → SQL）→ `ai_guard`（AST 守卫）→ `ai_nl2sql`（问数）→ `ai_evidence`（29 条数字溯源）→ `ai_report`（简报，正文零手打数字）→ `ai_eval`（30 条回归 **30/30**） |
| 谁读的 | 看板第 ⑤ 个页签；也可命令行直跑 `python scripts\ai_eval.py` |
| 一句话原则 | **模型负责理解人话，程序负责决定口径**——模型只输出指标计划 JSON，SQL 由模板拼，守卫再拦一道 |
| 和上一层差什么 | 前面每层都在"存数据"，这一层**只产生答案**；它不改任何 parquet，跑一百遍数据也不变 |

## 5. 已知反常（面试会被问）

| 反常 | 数字 | 说明 |
|---|---|---|
| **DWD 比 ODS 还大** | ODS 1,089.2 MB → DWD 1,217.3 MB（+11.7%） | 行数少了 49 行，体积反而大了。**推测**：去重时的 shuffle 打乱了原本基本按时间排的行序，Parquet 字典编码效果变差；另外小文件多反而让每段编码更局部。**此推测未实测验证** |
| 商品数少 886 | 体检 4,162,024 → `item_day` 4,161,138 | 只在越界时段出现过的商品 |
| 类目数少 2 | 体检 9,439 → `category_day` 9,437 | 同上 |
| 用户数少 3 | 体检 987,994 → DWS 987,991 | 41,450 个用户碰过越界行，但**只有 3 个人的全部记录都在窗口外** |
| 8 天档有个鼓包 | 出现 8 天的商品 198,182 > 出现 7 天的 188,415 | 最可能是窗口边界效应，未深究 |
| 日 `buy_rate`（购买率）18%–21%，但 9 天累计 68.06% | 行口径 `2,015,807 ÷ 100,095,182 = 2.01%`；日口径 `buy_uv ÷ uv` = 17.91%–20.69%；9 天人口径 `672,404 ÷ 987,991 = 68.06%` | **同一个名字三个口径，最大差 34 倍**（2.01% vs 68.06%）。日报的分子分母都是"当天"，累计的都是"9 天"。**引用转化率必须写清周期与分母是人还是次数** |
| 留存率远高于真实电商（次日 78%–80%） | `6,968,544 ÷ 987,991 = 7.05`（平均每人 9 天里出现 7 天）；次日留存 `0.7773–0.7963`；3 日留存 `0.7592–0.7838` | 数据里没有"只来一次就走的人"，人人几乎天天来，留存必然高。**留存只能做相对比较，不能当行业指标引用** |
| 12-01/12-02 的次日留存跳到 98% | `970,401 ÷ 987,991 = 98.22%`；`d1_rate`（次日留存率）12-01 = `0.9825`、12-02 = `0.9798` | **不是算法错**。12-02 那天全体用户 98.2% 都在场，任何"留存到 12-02"的比例，理论上限就是 98% |
| 11-29 的 3 日留存（0.9850）> 次日留存（0.7956） | `ret_3d ÷ uv = 708,136 ÷ 718,922 = 0.9850`；`ret_1d ÷ uv = 571,944 ÷ 718,922 = 0.7956` | 留存率不只依赖"隔几天"，更依赖"**落在哪一天**"。11-29 的次日落在正常日 11-30，3 日落在全员日 12-02。**所以不能给留存加"必须单调下降"的断言** |
| 超过一半的购买不走"浏览→加购→购买" | 日口径 **56.0%–58.6%**；11-25 当天 `buy_pv_nocart`（看了、买了、没加购）66,810 人 > 标准路径 `s3_uv` 57,737 人；9 天口径 `672,404 − 528,408 = 143,996` 人，21.42% | 时序漏斗描述的**不是主要路径**。这是采用集合漏斗的**实证依据**，不是推测。注意 56% 是日口径、21% 是 9 天口径——两者都对 |
| 日漏斗转化率 7.7%–9.0%，9 天累计 53.69% | `r_total`（浏览→购买率）日 `0.0770–0.0895`；9 天 `528,408 ÷ 984,105 = 53.69%` | 日口径要求三个动作**同一天**发生；9 天口径只要**期内都发生过**。**差 6 倍**。同一件事换个窗口就能讲出两个结论，所以转化率必须带周期 |
| F 三分位点 = 1 / 3，三分之一买家只买过一次 | `P33 = 1`、`P67 = 3`；均值 `3.0`（`2,015,807 ÷ 672,404`）、中位数 `2` | 右偏。分档点由 `approxQuantile` 在**买家内部**现算，不含 315,587 个买 0 次的人——否则 P33 会变成 0，F1 档直接失效 |
| `R1_F1`（刚买 1 次）的 `avg_actions` 79.5 ≈ `RN`（从未购买）78.9 | `R1_F1` 66,457 人，`avg_actions` `79.5`；`RN` 315,587 人，`avg_actions` `78.9`；差 `0.6`（0.8%） | 首购没有带来活跃度提升。配合"只买 1 次的 228,546 人中 113,623 人已在 `R3`"一起看：**流失发生在首购之后，不在拉新环节** |
| `R3_F3` 25,144 人：买过 4 次以上但 5 天以上没再买 | `uv` `25,144`；`avg_recency` `4.99` 天；`avg_buy_times` `5.48`；占买家 `3.74%` | 高价值流失客群。只看 R 会判成流失，只看 F 会判成核心客户，**只有二维交叉才看得见** |

## 7. 维护规则（每次处理完数据照这个改）

跑完一个新脚本、数据发生变化时，**只需要改五处**：

1. **第 1 节目录总览**：加/改那一行（路径 · 分区数 · 文件数 · 大小 · 行数）
2. **第 2 节**：给它新开一个 `###` 小节，按「绝对路径 / 是什么 / 存了什么（列） / 行数 / 文件 / 谁写的 / 谁读的 / 和上一层差什么」填
3. **第 3 节表格**：加一行（脚本 · 输入 · 动作 · 输出 · 行数变化）
4. **第 4 节守恒**：如果总行数变了或多了新的分流，改等式；没变就不用动
5. **程序类（看板 / AI 层）**：不新增数据小节，改第 2 节末尾那个「程序，不产生数据」的说明框 + 第 3 节表格补一行

**打勾时机**：验证通过（assert 全绿）才改，不是代码跑完就改。
