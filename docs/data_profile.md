## 1. 规模

**测了什么**：`scripts/01_profile.py` 段 1，在一次 `agg` 内用三个
`countDistinct` 同时算出去重用户 / 商品 / 类目（**一次 shuffle，不是三次**）。
总行数由两条路径互证：`scripts/00_count.py` 的 `count()`，以及段 2
「四种行为行数相加」。

| 指标 | 数值 | 口径 |
|---|---|---|
| 总行数（行为记录条数） | 100,150,807 | **全量**（含 55,576 行窗口外记录） |
| 去重用户数 | 987,994 | 全量 |
| 去重商品数 | 4,162,024 | 全量 |
| 去重类目数 | 9,439 | 全量 |

**这意味着什么**：

- 平均每个用户产生约 **101 条**行为记录（100,150,807 ÷ 987,994）。
- 平均每件商品被交互约 **24 次**（100,150,807 ÷ 4,162,024），
  其中纯浏览约 **21.6 次**（89,716,264 ÷ 4,162,024）。
  **两个都是平均值，且被爆款严重拉高**——416 万件商品里绝大部分是冷门货，
  中位数会低得多。
- 9,439 个类目装下 416 万件商品，平均每类目 **441 件**；**这个平均同样失真**，
  类目分布极不均匀，热门类目上万件、冷门类目可能只有 1 件。

**对下游的影响**：

- 1 亿行 / 3.4GB，本地 PySpark 单机跑得动，**不需要集群**。
  **实测依据**：`02_check_item_cat.py` 对全量做「两列去重 + 两次 count」，
  耗时 **58.8 秒**。
- 商品粒度 416 万，「每商品一行」的宽表不划算。
  DWS 商品日表的**理论上界**是 4,162,024 × 9 ≈ 3,746 万行，但**实际远小于此**
  ——绝大多数商品只在一两天内出现过。**真实行数需在 DWS 阶段实测，本文不预判。**
- 类目只有 9,439 个，适合做**强汇总**的 ADS 看板与 AI 问答的主维度。

**本节的数字不能回答什么（边界）**：

- 987,994 **不是淘宝全部用户**，只是这 9 天内有行为的人；拉新率、用户大盘这类
  问题，本数据集一概答不了。
- 4,162,024 **不是全站商品数**，只是被交互过的商品；动销率的分母缺失。
- 「101 条/人」是**平均数**，中位数未知，**不能当"典型用户"来描述**。
- 本数据集是**经过筛选的样本，不是全站流量的随机切片**：去重用户中有
  **68.06%（672,404 / 987,994）**产生过购买行为，远高于真实电商 1–5% 的
  「访问→下单」转化水平。因此**本数据集的绝对转化率不可外推**，
  后续分析只做人群之间、商品之间、日期之间的**相对比较**。
## 2. 构成

**测了什么**：`scripts/01_profile.py` 段 2 用 `groupBy("behavior_type").count()`
数「行」；段 2b 在同一个 `groupBy` 上改用 `countDistinct("user_id")` 数「人」。
**两个分母不同**：行占比的分母是全量 100,150,807 行，用户占比的分母是
全量去重用户 987,994 人。

| 行为 | 行数 | 行占比 | 去重用户 | 用户占比 | 人均次数 |
|---|---|---|---|---|---|
| pv   | 89,716,264 | 89.58% | 984,114 | 99.61% | 91.2 |
| cart |  5,530,446 |  5.52% | 738,996 | 74.80% |  7.5 |
| buy  |  2,015,839 |  2.01% | 672,404 | 68.06% |  3.0 |
| fav  |  2,888,258 |  2.88% | 389,823 | 39.46% |  7.4 |
| **合计** | **100,150,807** | **100%** | **987,994**（不可相加） | — | **101.4** |

> 人均次数 = 该行为行数 ÷ 该行为去重用户数（如 buy：2,015,839 ÷ 672,404 ≈ 3.0）。
> 合计行的人均次数 = 总行数 ÷ 总用户数 = 100,150,807 ÷ 987,994 ≈ 101.4。

**这意味着什么**：

1. **「行占比」和「用户占比」是两个完全不同的东西，且差距极大**：
   buy 只占全部行为的 **2.01%**，但 **68.06% 的用户**产生过购买行为——**相差 34 倍**。
   任何只引用其中一个数的说法都是误导。
2. **行为强度差异巨大**：人均浏览 **91.2 次**，人均加购 **7.5 次**，
   人均购买仅 **3.0 次**。用户是「大量浏览、少量决策」。
3. **四种行为行数相加 = 100,150,807 = 总行数** → 不存在第五种行为，
   也没有解析漏行（这是一次对账）。
4. **漏斗是倒挂的，不能用经典顺序**：
   - fav 用户占 **39.46%**，**低于** buy 用户的 **68.06%**——「收藏过的人」比
     「买过的人」少 28 万。正常电商不可能出现「买的人比收藏的人多」。
   - **987,994 − 984,114 = 3,880 个用户一次 pv 都没有**，却有加购/收藏/购买记录。

**对下游的影响**：

- **漏斗不能按 pv → fav → buy 逐级算转化**，只能按「该用户在窗口内做过哪些行为」
  做集合分层（详见第 5 节约束）。
- 绝对转化率不可外推（理由见第 1 节边界）。

**本节回答不了什么**：

- **答不了真实转化率**：本数据集是筛选样本，68% 的购买率不是真实电商水平。
- **答不了「不收藏」的原因**：分不清是用户不想收藏，还是这份数据没记录。
- **答不了金额类指标**：无金额字段，GMV / 客单价 / ARPU 一概做不了。

## 3. 时间

**测了什么**：`scripts/01_profile.py` 段 5 取全量与窗口内的 `min/max`；
段 6 按**北京日**分组统计并做两条断言对账（天数 = 9、合计 = 窗口内总量）；
段 7 按 **UTC 日**分组（`ts − 8×3600` 后再 `from_unixtime`）作为对照。

**全量口径**（**不可直接引用**）：

| | 值 |
|---|---|
| min_ts | −2,134,949,234（≈1902 年） |
| max_ts | 2,122,867,355（≈2037 年） |

> ⚠️ **这两个数被极值污染，不代表数据的真实跨度**。它们只是"范围两头"，
> 中间绝大部分数据都在 2017 年 11 月 25 日 – 12 月 3 日之间。

**窗口内口径**（分析真正使用的范围）：

| | 值 |
|---|---|
| 窗口（左闭右开） | 1,511,539,200 ~ 1,512,316,800 |
| 对应北京时间 | 2017-11-25 00:00:00 ~ 2017-12-04 00:00:00 |
| 窗口内行数 | **100,095,231** |
| 窗口外行数 | **55,576** |
| 全量 − 窗口内 | 100,150,807 − 100,095,231 = **55,576** ✔（双路复算） |

**北京日逐日行数**（段 6，合计 = 100,095,231，对账 = [OK]）：

| 日期 | 行数 | 星期 |
|---|---|---|
| 2017-11-25 | 10,420,015 | 六 |
| 2017-11-26 | 10,664,602 | 日 |
| 2017-11-27 | 10,101,147 | 一 |
| 2017-11-28 | 9,878,190 | 二 |
| 2017-11-29 | 10,284,073 | 三 |
| 2017-11-30 | 10,447,740 | 四 |
| 2017-12-01 | 10,859,436 | 五 |
| 2017-12-02 | 13,777,869 | 六 |
| 2017-12-03 | 13,662,159 | 日 |

**UTC 日**（段 7，共 10 天）：11-24 **1,181,431**、11-25 10,511,605、
11-26 10,571,046、11-27 10,013,457、11-28 9,884,189、11-29 10,319,060、
11-30 10,541,698、12-01 11,171,515、12-02 13,940,949、12-03 11,960,275。

**这意味着什么**：

1. **为什么按北京切是 9 天、按 UTC 切是 10 天**：原始 `timestamp` 是 **UTC 秒**，
   北京时间 = UTC+8。UTC 的 11-24 16:00 正好是北京 11-25 00:00，
   所以 **UTC 的「11-24」只装了北京 11-25 凌晨 0–8 点这 8 小时**。
2. **那 1,181,431 行不是「另一天的人」**，是同一批用户被时区切成了两截。
   佐证：418 万÷… → 该 8 小时速率约 **41 行/秒**，全天平均约 **129 行/秒**，
   **约为全天的 1/3**，符合"凌晨流量低"的真实作息。
3. **12-02 / 12-03 明显翘尾**：两天日均约 **13,720,000**，前 7 天日均
   **10,379,315**，高约 **32%**。但 11-25 / 11-26 同为周末却基本持平
   （较前 7 日均值 +0.4% / +2.7%），**所以这不是「周末效应」**。
   **推测**与双 12 预热有关（**假设，本文不作结论**）。
4. **日均行数上涨，分不清是"人多了"还是"人均点多了"**——必须用每日
   **去重用户数（UV）** 才能判断，留待 DWS 阶段回答。

**对下游的影响**：

- ODS **只保留窗口内** 100,095,231 行按 `dt`（北京日）分区；
  超出窗口的 55,576 行**不删除、单独隔离**（见第 4 节）。
- 所有日粒度指标一律以**北京日**为准，UTC 口径仅用于校验，不进入 ADS。
- 留存计算只有 9 天，**次日 / 3 日留存可做，7 日勉强，月度留存绝对不做**。

**本节回答不了什么**：

- **答不了长期趋势**：只有 9 天，看不到周/月/季节规律。
- **答不了"12-02 为什么涨"**：缺外部信息（活动、投放、天气），只能说"涨了"。

## 4. 质量问题（最重要的一节）

**测了什么**：`01_profile.py` 段 3（空值）、段 4（非法行为值）、段 5（时间越界）、
段 8（完全重复）；`02_check_item_cat.py`（商品与类目的唯一性）。
时间越界的四类细分由独立 Python 流式扫描脚本得出，并用
「全量 − 窗口内 = 55,576」双路复算验证一致。

| # | 问题 | 数量 | 占比 | 处置 |
|---|---|---|---|---|
| 1 | 时间戳早于窗口 | 52,830 | | 隔离 → `dwd_bad_record` |
| 2 | 时间戳晚于窗口 | 2,398 | | 隔离 → `dwd_bad_record` |
| 3 | 时间戳为负数 | 318 | | 隔离 → `dwd_bad_record` |
| 4 | 时间戳 ≥ 2×10⁹（≈2037 年） | 30 | | 隔离 → `dwd_bad_record` |
|  | **越界合计** | **55,576** | **0.05549%** | |
| 5 | 按 (user_id,item_id,behavior_type,ts) 四列键判定重复 | 49 | 0.000049% | 待 DWD 阶段下钻确认后决定：丢弃 or 保留 |
| 6 | 商品对应多个类目 | 1,418（配对数） | 0.0341% | **保留**，见下 |
| 7 | 五列空值 | 0 | 0 | 无需处理 |
| 8 | 非法 behavior_type | 0 | 0 | 无需处理 |
| 9 | 字段数 ≠ 5 的行 | 0 | 0 | **排除解析错位** |

> 第 1–4 类**互斥且穷尽**：52,830 + 2,398 + 318 + 30 = **55,576** ✔
> 这本身就是一次对账。

**这意味着什么**：

1. **越界数据不是"垃圾"，而是"边界溢出"**：55,576 行里 **100% 是 pv**，
   涉及 **41,450** 个去重用户——不是几个坏 ID 刷出来的，而是**分散的真实用户**。
   其中约 4 万行落在 2017-11-24，是**真实的浏览记录**，只是不在分析窗口内。
2. **不能直接 `filter` 掉**：删掉等于篡改原始数据，且会失去"为什么被排除"的证据。
   **正确做法是 ODS 原样保留 → DWD 隔离到 `dwd_bad_record` 并记录原因。**
3. **重复率 0.000049% 极低，但去重这一步不能省**：重复率低是因为**公开数据集
   已清洗过**；换到生产环境，同一用户在同一秒的重复上报非常常见。
   **流水线的正确性不能依赖"这批数据恰好干净"。**
4. **商品多类目是真实业务行为，不是脏数据**：对 `item_id` 下钻可见两个类目的
   时间区间**完全不重叠**（如某商品 11-26 前均为类目 A，11-29 起变为类目 B）。
   若为数据错乱，同一时段内会出现类目来回跳。判定为**商品中途调整类目**，
   **保留不删**。
5. **因此 `category_id` 是「随行变化的时变属性」**，不能建静态商品维表去 join
   ——静态维表只能存一个类目，会把历史行为错误地重算成新类目。

**对下游的影响**：

- DWD 需要一张 `dwd_bad_record` 表，字段：原始五列 + `bad_reason` + `ingest_time`。
- DWD 去重键 = `(user_id, item_id, behavior_type, ts)`。
- DWS 聚合直接用**每行事实数据自带的** `category_id`，**不 join 商品维表**。

### 4.1 重复数据下钻

**怎么查的**：对 ODS 主表（窗口内 100,095,231 行）按 `user_id + item_id + behavior_type + ts` 四列分组，取组内条数 > 1 的组，再把这批键**广播**回原表回捞原始行。一次性工具 `scripts\check_dup.py`，不占正式步骤编号。

**查出什么**：

| 指标 | 值 | 说明 |
|---|---|---|
| 重复组数 | **49** | 与 `04_dwd.py` 的 `[3] 重复 = 49` 一致 |
| 每组条数 | **全部为 2** | 无 3 条以上，不存在连续多次重传 |
| 涉及原始行数 | **98** | 49 组 × 2 行 |
| 应删除行数 | **49** | 98 − 49，每组保留 1 条 |
| 五列是否完全相同（含 `category_id`） | **是** | 同组内类目不一致的组数 = 0，故四列键与五列全同结果一致 |
| 行为分布 | **`buy` 约 2/3，`pv` 约 1/3**（按行计） | 组数 = 行数 ÷ 2 |
| 分布位置 | **全部在窗口内** | 越界表 55,576 行零重复 |

**这意味什么**：

`buy` 在重复中占比约 66.7%，而其整体占比仅 2.01%，**富集约 33 倍**。符合事务性行为（下单）带客户端重试与回执确认、网络抖动时重复上报的机制特征。

另观察到 3 处「同一秒、同一用户、**两个不同商品各自**重复一次」，说明是**整批上报重传**，而非单条消息重试——问题定位在客户端批量上报的重试机制，不是某个字段坏了。

**所以怎么处理**：**删副本、留一份，不进 `dwd_bad_record`**。判据是「删了还能不能恢复」——重复行是**同一事实的冗余副本**，留一份即无损；越界行是**独立事实**，删一份即永久丢失。

**为什么 49 组全在窗口内**：去重键含 `ts`，`ts` 唯一决定窗口归属，同一重复对的两行 `ts` 必然相同，故必不跨窗口。由「窗口内 49 + 窗口外 X = 全量 49」推得 X = 0，与「越界表零重复」互证。

**本节回答不了什么**：

- **答不了"原本正确的值是什么"**：越界时间戳无法还原真实时间，只能隔离。
- **答不了"类目变更的生效时间"**：数据里只有"第一次以新类目出现的时间"，
  没有官方变更时间。


## 5. 下游影响（给后面每一层的约束）

**验收标准**：

| 层 | 验收指标 | 期望值 | 说明 |
|---|---|---|---|
| DWD 主表 | **100,095,182** | = 100,095,231 − 49（窗口内行数减去重复） |
| DWD 次品筐 | **55,576** | 四类相加：52,830 + 2,398 + 318 + 30 |
| DWD 三段守恒 | **100,095,182 + 49 + 55,576 = 100,150,807** | 已于 `04_dwd.py` 内以 `assert` 固化 |
| 次品筐是否去重 | **否** | 证据箱只贴标签、不动内容；同一条脏数据上报两次也是两次的事实 |
| `_SUCCESS` 可用性 | **不可作为完成标志** | `partitionOverwriteMode=dynamic`（动态分区覆盖）不做整目录原子提交，分区表不落 `_SUCCESS`；改用行数守恒 + 双路对数 + `_temporary` 不存在 |

**数据边界（写死在方案里，防止后面越界发挥）**：

1. **无金额字段** → 不做 GMV、客单价、ARPU、RFM 中的 **M（金额）**。
   RFM 只能做 **R（最近购买）** 和 **F（购买频次）**。
2. **类目只有 ID、没有名称** → DWS/ADS **不硬造类目名**，
   只用 ID 或「类目 A/B/C」这类中性标签。
3. **只有 9 天** → 留存只做**次日**与**3 日**；不做 7 日以上的留存，**绝不做月度留存**。
4. **样本经过筛选（68% 购买率）** → 绝对转化率**不可外推**，
   只做人群 / 商品 / 日期之间的**相对比较**。

### 漏斗设计的硬约束（来自第 2 节的数据事实）

1. **禁用逐级转化漏斗**（pv → fav/cart → buy）。原因：fav 用户占比 39.46%
   低于 buy 用户占比 68.06%，且 **3,880 个用户零 pv 却有购买记录**，
   行为序列不完整，逐级相减会得到负数或虚假流失。
2. **改为「行为集合分层」**：按用户在窗口内「做过哪些行为」的组合分层
   （如「只看过」「看过+加购」「看过+加购+购买」「直接购买」等），
   每层统计人数与该层内的行为强度。
3. **DWS 的 user×日 表必须保留四个行为的存在性标记**
   （has_pv / has_cart / has_fav / has_buy），供 ADS 做集合分层。
   **否则 DWS 需返工。**

### 类目相关约束

4. **不建静态商品维表**、不做 `item → category` 的 join。
   DWS 类目粒度直接用事实行自带的 `category_id`。

**本节回答不了什么**：

- 本节的验收标准是**基于阶段 A 的体检结论**，若后续发现新的数据问题，
  这些标准需要同步修订——**验收标准是有版本的概念，不是一次写死的。**
